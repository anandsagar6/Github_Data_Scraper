----------------------------------------
1. WHY I WANT THIS - THE GOAL
----------------------------------------

I clone and pull this project onto different systems, and then immediately run
it. So the repository has exactly two jobs:

  (A) A fresh `git clone` or a `git pull` MUST contain every single file and
      folder needed to run the project correctly. Not one necessary file may be
      missing. If something is required to start the script or to make it behave
      the way I expect, it belongs in git - no exceptions.

  (B) The repository must NOT carry any file that the script itself creates
      after it starts running. When I clone on a new machine I want a clean
      start, not another machine's leftover output, progress position, cache or
      logs.

Those two rules decide everything. If you are ever unsure about a file, apply
this test:

      "If this file is missing on a fresh clone, does the script fail,
       refuse to start, or behave incorrectly?"

  - YES, it breaks or misbehaves  -> the file MUST be tracked. Never ignore it.
  - NO, the script recreates or re-initializes it automatically -> ignore it.

When you genuinely cannot tell, DEFAULT TO TRACKING THE FILE. A redundant file
in git is a minor annoyance; a missing required file breaks the project on every
machine I clone to. Never guess in the direction of ignoring.

----------------------------------------
2. NON-NEGOTIABLE RULES
----------------------------------------

RULE 1 - NEVER ignore credentials or secrets.
  Do NOT add the usual boilerplate secret patterns. Specifically, do NOT write
  rules for things like:
        .env / .env.*
        *.pem / *.key / *.crt / id_rsa
        credentials.json / client_secret*.json / service_account*.json
        token.json / secrets.* / config.ini / settings.local.*
        api_keys.* / auth.json
  If this project needs a credential, API key, token, cookie file, service
  account, login config or any other secret to run, that file MUST be committed
  so it arrives with every clone and pull. This is an intentional decision for
  this workflow - do not "helpfully" protect secrets here, and do not add such a
  rule commented-out or as a suggestion. Leave them fully tracked and silent.

RULE 2 - NEVER ignore anything required to run the project.
  Source code, libraries and helper modules, configuration, data/seed/input
  files the script reads, lookup or mapping tables, templates, dependency
  manifests (requirements.txt, package.json, Pipfile, pyproject.toml, lock
  files), helper and maintenance scripts, tests, and documentation all stay
  tracked.

RULE 3 - Use EXACT filenames, not broad extension globs.
  Write `/current_data.xlsx`, never `*.xlsx`. Write `/progress_state.json`,
  never `*.json`. Broad globs are the main way a required config or input file
  gets silently left out of git months later when someone adds it. A pattern
  with a wildcard is acceptable ONLY where the script generates a genuine family
  of files whose names it builds at runtime - for example numbered cycle or
  batch outputs (`/current_data_cycle*.xlsx`), timestamped logs, or sidecar
  `*.lock` / `*.tmp` files. In that case keep the stem as specific as possible.

RULE 4 - Ignore only files the script RE-CREATES automatically.
  Before ignoring any file, confirm in the source that the script creates it, or
  re-initializes it, when it is missing. If a file is written by the script but
  the script would fail or lose something irreplaceable without it, treat it as
  required and track it - and tell me about it in your summary.

Do not produce a generic template from memory. Derive the list from this

  a) List the project tree, including dotfiles, excluding dependency and

  b) Find every path the code WRITES. Search the source for the write paths and

  d) Look for an existing reset / cleanup / clear-state script in the project

     the current source, since it can fall behind.

  e) Check where the test suite writes its fixtures. If tests create files
     inside the repository rather than in a system temp directory, account for
     that; if they use temp directories, nothing is needed.

  f) Determine the runtime/dependency directory actually used by this project
     (venv/, .venv/, node_modules/, __pycache__/, target/, build/, vendor/) so
     it can be ignored while its manifest stays tracked.

  g) If a .gitignore already exists, read it first. Then update it rather than

4. CLASSIFY WHAT YOU FOUND
----------------------------------------

Sort every discovered path into IGNORE or TRACK, and group the IGNORE list into
these categories (skip any category this project does not have):

  IGNORE
    1. Primary output / result files the script produces
       (the "current data" file, the active working output)
    2. Cycle / batch / rotated / numbered / timestamped output files
       (completed chunks, per-run archives)
    3. Progress, checkpoint, resume-position and counter state

    4. Caches and derived data the script can rebuild by re-fetching
    5. Logs, error/evidence files, and run reports
    6. Pacing, scheduling, rate-limit, authorization-block or session state
    7. Sidecar lock files and atomic-write temp files
    8. Dependency/environment directories and compiled bytecode
    9. Editor and OS clutter, including the lock files office apps create next
       to an open spreadsheet or document

  TRACK (never ignore)
    - all source, modules, helpers, tests, docs
    - dependency manifests and lock files
    - configuration and input/seed/lookup data the script reads
    - every credential / secret / auth file needed to run (see RULE 1)

5. HOW TO WRITE THE FILE
----------------------------------------

  - Anchor root-level runtime files with a leading slash (`/state.json`) so the
    rule cannot accidentally match a same-named file in a subdirectory.

  - CRITICAL SYNTAX WARNING: git does NOT support trailing comments on a pattern
    line. A `#` only begins a comment at the START of a line. Writing
        /current_data.xlsx    # active output
    makes git treat the whole thing - spaces, `#` and all - as a literal
    pattern, so it silently matches nothing and the file gets committed anyway.
    Put every comment on its own line, above the pattern it describes.

  - Organize the file into clearly labelled sections matching the categories in
    part 4, and comment each entry with what creates it and what it is for, so a
    future reader can maintain it. Where useful, name the source constant or
    variable the filename comes from.

  - Open the file with a header block stating the purpose: that a clone must be
    runnable, that only script-generated runtime files are ignored, that
    credentials and secrets are intentionally tracked, and that exact filenames
    are used on purpose. Include the quick-start commands for the project.

  - End with a "safety net" section that explicitly re-includes the essential
    files with `!` negations (`!/main_script.py`, `!/requirements.txt`,
    `!/test/`, `!/test/**`, `!.gitignore`, and any credential/config file the
    project needs). These are no-ops today; they exist so a careless broad rule
    added later cannot drop a required file. Note that a `!` negation cannot
    rescue a file whose parent directory is excluded.
